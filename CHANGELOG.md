# Changelog

Release history for [fold](README.md), newest first. The compatibility
contract these entries are written against is
[API stability](README.md#api-stability).

## Unreleased

Icons survive federation, two canaries for the class of bug that hid it, three ways the audit path reached back into the request it was recording, a revoked signing key that stayed trusted, a discovery-only gateway that came up ready with nothing in it, four postures the gateway accepted without a word, two host allowlists that each left one door unchecked, four ways one caller or one upstream could cost the whole process, a process that exited wrong at both ends, a chart that promised zero-downtime rollouts and had none of the parts, nothing that checked a chart install or a deployment after the fact, packaged alerts that named error codes fold stopped minting while nothing paged on an outage, a release pipeline that trusted three things it never pinned, deploy artifacts that described a cluster they could not be applied to, and documentation that still called shipped features proposed.

- **The documentation still called shipped features proposed.** Two design records — the external decision hook and policy depth — opened with `Status: proposed` for code that has been in `gateway/hook.go` and `policy/policy.go` for several releases; the roadmap's items 9, 13, and 14 carried no **shipped** marker though the hook, `policy.serverInitiatedDecision`, and `pinDefinitions` all exist; and README's "Not implemented" cited item 13 as an unresolved dependency of the multi-round-trip gap when the half it depends on is the one not yet designed. Each now says what shipped, in which shape, and what remains. The request-pipeline diagram gains the decision hook's ingress and egress stages, which were the two steps it drew without. And the downstream stdio gap — fold has no stdio front door; `fold-stdio` is upstream-side only — was recorded nowhere but the tail of a design record, which is how a decision reads as an oversight; it is now a README "Not implemented" entry and a roadmap non-goal, with the reasoning. `docs/deploy.md`'s example versions (`v0.7.0`, which never existed, and `v1.11.0`) name the current release.

  Two policy claims are new rather than corrected. **`SECURITY.md` gains a supported-versions table** — the latest minor for everything, the previous minor for exploitable issues for 90 days after the next ships — with a disclosure section (patch release, GHSA and CVE where one applies, up to 90 days before public disclosure) and a channel for reporters who cannot use GitHub's private reporting. And **`.github/CODEOWNERS`** names an owner for every path. The launch plan's go/no-go gate, which tested the demo and the quickstart, now also tests what an evaluator installs that afternoon: `helm install` from the OCI registry plus `helm test`, the container's health check, the smoke script against the demo, attestation verification from a machine that is not the maintainer's, and the discovery manifest applying on a fresh cluster.

- **The deploy artifacts described a cluster they could not be applied to.** `deploy/fold-discovery.yaml` — the only manifest shipped for the producer, and the one the release archive carries — referenced a `fold` namespace it never created and a `fold-discovery-token` Secret it never mentioned, so `kubectl apply -f` on a clean cluster failed outright and, once the namespace existed, left the pod in `CreateContainerConfigError` with nothing saying why. Its pod spec lacked `runAsNonRoot` and a `seccompProfile`, so a `restricted` Pod Security namespace rejected it; it granted a `ClusterRole` by default when the common case is one namespace; it pinned `:latest`; and its own trailing comment pointed the gateway at an `http://` Service URL the gateway refuses. The file now creates the namespace (labelled `restricted`), documents the two-step apply with the `kubectl create secret` command, runs under the same security context the chart uses, grants a namespaced `Role` with `--namespace fold` and keeps the cluster-wide variant commented beside it, gains a liveness probe, and leads with the loopback sidecar `discovery.url` that works with nothing else installed.

  **The images had no OCI labels and no `HEALTHCHECK`**, so a registry UI could not link an image to its commit, an admission policy had no `revision` to key on, and a plain `docker run` reported no health although `fold --healthcheck` has existed since the compose stack needed it. All four Dockerfiles now carry `org.opencontainers.image.{title,description,source,url,documentation,licenses,version,revision}` — `revision` from a `REVISION` build argument both workflows pass as the commit SHA — and the gateway image declares its own probe. The `stdio.Dockerfile` header named a `Dockerfile.stdio` that does not exist; it names the real path. `.dockerignore` gains the test binaries, coverage file, goreleaser output, and compose state that were being sent as build context.

  **`tracing` and the `otlp-logs` sink had no runnable example.** Both are first-class config and the example config already pointed at `otel-collector:4318`, but nothing in the repository was listening there. The compose observability profile now runs an OpenTelemetry Collector on that name from `deploy/observability/otel-collector.yaml`, receiving spans and audit events on one OTLP/HTTP endpoint and printing both — the smallest thing that makes the two paths demonstrable, with the exporter to swap for a real backend called out.

- **The release pipeline trusted three things it never pinned.** `compose.yaml` pinned `ghcr.io/fold-run/fold:v1.11.0` with a comment saying the release flow bumped it; the release skill said compose pinned `:latest` deliberately and to leave it alone. Neither was true, and the file sat four minor releases behind the repo it lived in — so `make compose-up` ran a gateway that predated the error-code renumbering while the alert rules the observability profile mounts described the codes it did not emit. The three hand-pinned image tags (compose's `fold` and `fold-stdio`, and `deploy/fold-discovery.yaml`'s producer, which was `:latest`) are now held equal to the chart's `appVersion` by `gateway/release_pins_test.go`, which is the one version the release workflow already refuses to publish wrong, and the release skill's step says to bump them together.

  **`:latest` moved on any `v*` tag**, release candidates included, and goreleaser published every tag as a full release. A `v1.16.0-rc1` would have become what `docker run ghcr.io/fold-run/fold` — the README's first command — resolved to. All four images now tag `:latest` only when the tag carries no pre-release suffix, and goreleaser marks suffixed tags as GitHub pre-releases.

  **Nothing checked the release from the outside.** The `binaries`, `chart`, and `image` jobs were independent, so a GitHub release existed the moment `binaries` finished, advertising images that a failing `image` job never pushed; and every artifact was attested by the job that built it without anything confirming the attestations verified. A `verify` job now runs after all three: it downloads one archive and the checksums and verifies both against their attestations, verifies all four image digests, and pulls the chart from the registry and verifies it — the first checks the release-verifier agent performs, as a gate rather than a human step.

  Two smaller pins from the same audit. `make vuln` ran `govulncheck@latest`, the one unpinned tool in a repository that pins every action by SHA and every base image by digest; it is now a `go.mod` tool dependency (`go tool govulncheck`), which Dependabot's Go group tracks like any other module. And `make fuzz` covered four of the seven fuzz targets — `FuzzSanitizeRawMeta`, `FuzzListCacheScope`, and `FuzzParamHeaderRelay` ran their seeds under `make test` and were never explored further — and fuzzing ran in no CI job at all. All seven are in `make fuzz`, and the weekly drift workflow runs it, opening the same tracking issue on a finding that it opens for SDK drift.

- **The packaged alerts named error codes fold stopped minting, and nothing paged on an outage.** v1.15.0 renumbered every minted code. `deploy/observability/alerts.yml` was updated; the chart's `PrometheusRule` — the copy most production deployments actually install — was not, so its runbook text still told an operator paged at 3am that the gateway was answering `-32041` and `-32044`, codes that appear nowhere in the codebase. The lockstep test that exists for exactly this compared the two files by alert *name*, and both files had the same names. Two tests now do what the name test could not: every `-3xxxx` in either rule file or the dashboard must be a code `upstream.go` or `tasks.go` mints, and the same alert in both files must have the same expression (with the chart's values substituted, so the chart defaults are pinned equal to the plain file's literals), the same `for`, the same severity, and the same summary. Descriptions are exempt on purpose — the chart's refer to values keys — which is why the code check covers them separately. Chart **0.4.2**.

  **Nothing paged.** All fifteen alerts were `warning` or `info`, and the operations guide said the readiness probe was fold's genuinely paging condition — true for a cluster with an external uptime monitor and false for the deployment that installed `prometheusRule.enabled` and believed itself covered. Two `critical` alerts now exist for the two shapes of "fold is not serving": `FoldDown` (a scrape target gone for two minutes, which with readiness on `/health` is also what a total upstream outage looks like from outside) and `FoldAllRequestsFailing` (`upstream_down` on more than 90% of requests for five minutes — the gateway up and honestly refusing while the federation is not serving). Two `warning` leak detectors join them, `FoldGoroutinesHigh` and `FoldMemoryHigh` on the Go and process collectors fold already registers, with a dashboard panel beside them: the growth a ten-second benchmark cannot see is the failure this pack had no eyes for. And the "what the alerts assume" table in the operations guide, which listed eleven of fifteen alerts and omitted the two that matter most — a lost audit trail and a Redis-degraded fleet — now lists all nineteen.

- **Nothing checked a chart install or a deployment after the fact.** The chart had strong `fail` guards for the mistakes that make a manifest *wrong* and no defence against the ones that make it *silently different*: `replicaCount: "2"`, `probes.readiness.timeout` for `timeoutSeconds`, a misspelt key — all rendered without complaint. Chart **0.4.1** ships `values.schema.json`, so `helm lint` and `helm install` refuse a wrong type or an unknown key at every level the chart owns; the objects it passes through to Kubernetes untouched (`config`, `resources`, `affinity`, `strategy`, …) stay free-form on purpose. `make helm-check` now lints `--strict` and asserts the schema rejects a non-integer `replicaCount`.

  And after `helm install` there was nothing to run. `helm test <release>` now runs the chart's own smoke script from a pod against the Service — `initialize`, `tools/list`, an optional `tools/call`, then `/health` and `/metrics` on whichever port it lives on, with the probe Host header — and the same script is `scripts/smoke.sh` for a laptop, a CI job, or `make compose-smoke` against the local stack. It is POSIX `sh` and `curl` only, so the test image is a pinned `curlimages/curl` and the script runs unchanged everywhere. It is the check to run after every upgrade, because a rollout that leaves pods Ready while answering an empty `tools/list` is exactly what readiness does not catch — and it fails on a `503` from `/health`, a `403` from a wrong Host, an `error` in the list, or a `/metrics` with no `fold_build_info`, each with a message that names the step.

- **`audit.scrub.redactUsageKeys` was redacting the client's response, not just the trail.** The `usage` map on an audit event is the upstream's own result `_meta.usage` — the gateway stores a pointer to it when the result comes back, hands the event to audit, and *then* serializes that same result to the caller. The scrub deleted keys from that map in place, so a control introduced to keep secrets out of the sinks was quietly taking fields away from the response, and the invisibility rule was broken in the one place a redaction feature is most likely to be turned on. The existing test built an isolated event and could not see it. The scrub now edits a copy; `gateway/auditscrub_test.go` calls a real upstream through fold with the scrub configured and asserts the client still has the key and the file sink does not.

- **The default audit sink wrote synchronously on the request goroutine.** `stdout` is the sink the quick start uses and the one most likely to be a pipe somebody else reads — a container log driver, a collector — and a pipe nobody is reading blocks its writer, under a mutex, for every request in the process. The webhook and OTLP sinks had always refused to be the reason a request is slow; `stdout` now refuses the same way, from a worker behind the same 1024-event buffer, dropping and counting on overflow (`fold_audit_events_total{sink="stdout",outcome="dropped"}` — a new label value on an existing metric, which the compatibility contract allows) and reporting `delivered` like the file sink already did. The `file` sink stays synchronous **on purpose**: it is the durability anchor `requireDurable` points at, and a buffered file would make that promise conditional on a clean shutdown. The configuration reference said delivery was asynchronous for every sink; it now says which.

- **A closing webhook sink abandoned its buffer, uncounted.** `Close` stopped the delivery worker and released the dead-letter file with up to 1024 events still queued and, worse, with a batch that had been mid-retry when shutdown arrived leaving the worker with no accounting at all — exactly at the moment a rolling restart makes the tail of the trail interesting, and in direct contradiction of the contract that a lost event is always countable. A closing sink now drains: each buffered batch gets one attempt inside a three-second bound, a post that was already in flight is aborted when that bound is spent rather than being allowed the client's full timeout, and whatever cannot be placed is dead-lettered where there is a `deadLetterPath` and counted as `dropped` where there is not. `stdout` closes the same way, counting what a wedged writer kept, including the event stuck inside the write.

- **A key the IdP revoked kept verifying tokens for the life of the process.** The JWKS cache declared a five-minute TTL, assigned it, and never read it: the only thing that prompted a refetch was a token presenting a `kid` the cached set did not have. That handles rotation-*in* — a new key appears, tokens start naming it, fold fetches — and it handles nothing about rotation-*out*. An identity provider that withdraws a compromised key does not send a notification; it stops publishing the key, and the tokens that were signed with it keep arriving with the same `kid` they always had. fold answered every one of them from the stale set. Rotation-in was tested; revocation was not, and `unused` did not flag the field because it is a struct member rather than a symbol. The cache now refreshes a set once it is older than the TTL regardless of what the token presents, single-flighted on the same per-URI gate as before, so `auth/auth_test.go` can revoke a key, advance the clock six minutes, and watch the token it signed stop verifying.

  Two things that fell out of doing it properly. A refresh that **fails** keeps serving the last good set — an IdP outage is not a reason to refuse every caller holding a valid token — and is retried at most every 30 seconds, because a refresh attempted on every verification against a failing endpoint, serialized behind the fetch gate, would turn the IdP's outage into a latency incident for everyone. And the fetch is now **observable**: `fold_jwks_fetches_total{issuer,outcome}` counts `ok`, `stale` (the refresh failed, the old set served), and `error` (nothing cached, verification failing), with `FoldJWKSFetchFailing` in both rule files and a dashboard panel. The inbound trust anchor had no telemetry of its own before this; an IdP outage failed every authenticated request and surfaced only as `unauthenticated` rejections at severity `info`, which is exactly what a wave of clients with bad tokens looks like.

- **The credential injector was wired to `http.DefaultClient`, against the codebase's own rule.** `auth/client.go` says of that client, verbatim, "never wire it here"; `gateway/upstream.go` did, for the client that calls upstream token endpoints. Those requests carry the most sensitive material fold handles and they are single-flighted per key, so a token endpoint that stopped answering held every caller for that key behind one request with no client-level timeout — bounded only by the request path's 60 s. The redirect refusal was already applied by construction; the timeout was not. Both call sites now take the bounded trust-anchor client, `NewUpstreamCredentials` falls back to it rather than to the default when given nothing, and a test pins that the fallback has a timeout.

- **A gateway whose only source of upstreams was down came up ready and served nothing.** A discovery-driven federation is the shape `fold-discovery` exists for: no static upstreams, everything arrives from the polled document. Its failure at boot was silent in three parts. The first sync failed and logged a warning, keeping the "current" set — which was empty. `/health` computed readiness from probeable upstreams alone, and with zero of them `healthy == probeable` held vacuously, so the pod answered `200 ok`, passed its readiness probe, and joined the Service. Every `tools/list` then fanned out to nothing and returned an empty list with no error, because an empty fan-out has no partial failure to report. The pod recovered on the next successful poll and nothing in the interval said anything was wrong — `fold_discovery_syncs_total{outcome="error"}` made it alertable, but nothing made it *unready*, and unready is what keeps a pod serving empty lists out of rotation.

  `/health` now answers `503` on a gateway with no upstreams whose discovery source has never been applied, and carries a `discovery` object (`lastOutcome`, `lastSyncAt`, `applied`) saying why — the response shape is frozen additive, so the new field is within the contract, and `fold --healthcheck` treats any answer as alive, so the container check is unaffected. The condition is *never applied*, not *currently failing*: a source that goes down after a document has been applied keeps the last good set serving, as it always did, and a source that applies an **empty** document is `200` because the registry said the federation is empty and fold believes it. One consequence is written into the deploy guide rather than smoothed over: the startup probe's budget now also bounds how long a discovery-only pod's source may be down at boot before the pod is restarted, and a federation whose registry comes up slowly should raise it.

- **Four unsafe postures the gateway accepted silently now say so at startup, and one of them is closed.** fold's defaults are safe by *pairing*: auth is off out of the box because the listener binds loopback, and the quick start works with no IdP because nothing off the machine can reach it. Nothing checked the pair. `--host 0.0.0.0` on a config with no `auth` section was an open gateway whose only sign was an Info field reading `authRequired=false`, and it compounded: `/health`'s redaction of URLs, owners, and raw connect errors was gated on auth being *on*, so the same command published every upstream URL and every error string — which can name secret env vars — to anyone who could reach the port. `/health` is now redacted for every caller, whatever the auth mode; it is unauthenticated by design, and the detailed view belongs to `/api/federation`, which authenticates. The pair itself is now checked: auth off on a non-loopback bind logs a warning naming the exposure.

  Three more warnings, each for a posture validation accepts on purpose. A **credentialed upstream at `http://`** — `static`, `passthrough`, `token-exchange`, `client-credentials` — sends its credential, or the caller's own bearer token, in the clear; validation forces `https` onto every other place a credential travels and deliberately not here, because cleartext inside a mesh that encrypts the hop is a legitimate topology fold cannot tell from a mistake. Each such upstream is now named at startup (loopback exempt), and the security model records it as an accepted risk in those words. **EMA with neither `allowedAssertionTypes` nor `allowedClientIds`** — the allowlists v1.15.0's token-endpoint hardening added — still exchanges any correctly addressed IdP-signed JWT, exactly as `auth/ema.go` says in plain language; it now says so in the log too, mirroring what discovery has always done for its missing allowlists. And an **absent `policy` block** is an allow-all engine, which the deploy checklist stated and `docs/defaults.md` and README did not: README billed deny-by-default in three places without the qualifier, and the defaults review had no row for `policy` at all. Both now say what the code does. The four warnings are listed together under "Log streams" in the operations guide, so a hardened deployment can be checked by grepping for none of them.

- **Two host allowlists each left one door unchecked.** Both are additive fields; both defaults are unchanged; both gaps are now warned about at startup when the field is absent.

  **`allowedHosts: ["*"]` switched Origin validation off with it.** The Host and Origin checks lived inside one `if !wildcard`, on the reasoning that a deployment behind a proxy that validates Host has nothing left to check. MCP disagrees: the Origin check is what defends against DNS rebinding, and it is required however Host is handled. The obvious fix — require same-origin under the wildcard — would refuse the browser clients that work today, Inspector on `localhost:6274` against a `["*"]` gateway among them, and a changed meaning is what the compatibility contract forbids. So the rule becomes explicit instead: **`server.allowedOrigins`** names the Origins browser clients legitimately use (exact hostnames or `*.suffix`, matched against the Origin's host), applies on its own whatever `allowedHosts` says, and `["*"]` is the explicit any-origin form for an operator who accepts the exposure. Absent, the old derivation from `allowedHosts` stands — and a Host wildcard with no `allowedOrigins` is named in the startup log rather than inherited silently. Requests with no Origin, which is every non-browser client, are unaffected either way.

  **Discovery bounded where a secret could travel and not where an upstream could live.** `allowedCredentialHosts` applies only to credentialed entries, and the exposure it closes — a compromised source pointing a gateway-held secret at a host of its choosing — is real. But a source needs no secret to register an upstream at an arbitrary host, and doing so puts that host's tool names and descriptions, the instruction set a model acts on, into every caller's `tools/list`, with the gateway dialing the host on every fan-out. **`discovery.allowedUpstreamHosts`** bounds every discovered endpoint host, credentialed or not, with the same pattern rules and the same whole-document rejection as the other three; the chart's `NOTES.txt` and the deploy checklist list it beside them. A document with one disallowed host is rejected whole — the compliant sibling entry is not applied either — which is the discovery path's posture everywhere and is pinned by test.

- **Four ways one caller or one upstream could cost the whole process.** None of them a crash in the ordinary run; each a bound that was missing.

  **A body that never finished held a connection forever.** `ReadHeaderTimeout` bounds the headers and a `WriteTimeout` is off the table because MCP responses are streams, so a client that sent its headers and then dribbled one byte a minute of a sub-cap body held a connection and a goroutine indefinitely — `MaxBytesReader` bounds size, not time. A 30-second read deadline now covers the body: armed when a body-bearing request enters, lifted the moment the body reaches EOF (and again when the handler returns), so it bounds the *request* and never the response. That property holds because every handler fold mounts reads its body to EOF before answering — the SDK uses `io.ReadAll`, the token endpoint parses a form — and it is pinned by a test that runs a one-second tool call under a 200 ms deadline and expects it to succeed.

  **A panic in a plain HTTP handler was invisible.** `net/http` recovers a handler panic per connection, so the process survived, but it recovered into its own logger: not counted in `fold_panics_total`, no audit event, no slog line. Every handler outside the MCP dispatch was in that position — `/health`, `/icons`, the well-known documents, and `/oauth/token`, which is unauthenticated — so an operator paging on the panic counter, as the dashboard recommends, would have seen nothing while an open endpoint panicked on every request. A recover middleware now sits inside the body cap and outside the mux, counting under site `http`, emitting one audit event, and answering 500 when nothing has been written yet. It is deliberately not the outer recover `rescue.go` warns against: the MCP path's boundary stays where it was, below the SDK's dispatch, where audit can still see the request.

  **The subscription table was unbounded under passthrough.** It is keyed by a URI the caller chose, and under passthrough any URI resolves to the one upstream, so a single long-lived session could grow it without limit — the one per-caller map not behind `internal/bounded`, and for a reason: evicting an entry would orphan the upstream subscription behind it and break the ref-count every other subscriber depends on. The bound is a refusal instead. A session may hold at most 1024 subscriptions; the next is refused with `-32602` (a parameter the caller can change by unsubscribing, which is what that code already means for cursors — the frozen minted codes gain nothing) and the slot is back the moment one is released. Re-subscribing to a URI a session already holds is not a new subscription and is never refused.

  **`fold-stdio` had no panic containment at all.** The gateway recovers on thirteen goroutine sites with a metric and a stack trace; the shim recovered on none, so a panic in the sweeper, a pump, the stderr relay, or a probe ended the process and took every bridged stdio server with it. Each site now runs under a `rescue` mirroring the gateway's — a pump that panics still tears its own session down, a probe that panics still answers, as a failure rather than a swallowed "healthy" — counted in `Stats.Panics`, surfaced on the shim's `/health`, and exported as `fold_stdio_panics_total`.

- **The process exited wrong at both ends.** At the end: a SIGTERM that arrived while any client held an SSE stream — which on a busy gateway is every SIGTERM — waited out the 10 s drain, severed the stream, and then returned `Shutdown`'s deadline error, so a routine stop exited **1**. Kubernetes shows that as `Error` rather than `Completed`, compose and systemd read it as a failed unit, and restart-reason dashboards fill with crashes that were rollouts. The severing was always right; the exit code was not. A routine stop now exits 0 and logs `drain deadline passed` when it had to cut something, and the bound is a flag, `--drain-timeout` (default 10 s), so an operator whose grace period allows more can give streams more.

  At the beginning: Redis unreachable when a replica *started* was fatal — ping failed, `New` returned an error, the process exited 1 — while the identical outage one second later was survived per-instance from the local mirror, exactly as `docs/deploy.md` promises. Fail-closed at boot and fail-open at runtime is a rolling-restart hazard in one specific shape: a Redis blip during a deploy fails every new pod while the old pods, which would have ridden it out, are being terminated to make room, and the fleet goes to zero for an outage the design had already decided to survive. Boot is now fail-open like everything after it: the replica starts, logs `redis unreachable at startup` at `error` once, counts `fold_state_degraded_total{kind="startup"}` (a new value on a frozen label set, which the contract allows), and go-redis reconnects on the next operation that reaches Redis. A `redis://` URL that does not parse is still fatal — that is a typo, and typos should not start.

  One more thing said rather than smoothed: `fold --validate` checks the document's structure and cross-field rules and nothing that needs a running process — not that `secretRef` env vars are set, not that the EMA signing key parses, not that sink paths open or Redis answers or `metricsAddr` binds. README said "validated on startup (`fold --validate`)", which oversold it. The deploy guide now says precisely what the flag covers and why it stops there: the chart's validating init container runs without secrets mounted, by design, and a deeper `--validate` would break every Helm rollout.

The inbound trust anchor had no telemetry of its own before this; an IdP outage failed every authenticated request and surfaced only as `unauthenticated` rejections at severity `info`, which is exactly what a wave of clients with bad tokens looks like.

- **The credential injector was wired to `http.DefaultClient`, against the codebase's own rule.** `auth/client.go` says of that client, verbatim, "never wire it here"; `gateway/upstream.go` did, for the client that calls upstream token endpoints. Those requests carry the most sensitive material fold handles and they are single-flighted per key, so a token endpoint that stopped answering held every caller for that key behind one request with no client-level timeout — bounded only by the request path's 60 s. The redirect refusal was already applied by construction; the timeout was not. Both call sites now take the bounded trust-anchor client, `NewUpstreamCredentials` falls back to it rather than to the default when given nothing, and a test pins that the fallback has a timeout.

- **A gateway whose only source of upstreams was down came up ready and served nothing.** A discovery-driven federation is the shape `fold-discovery` exists for: no static upstreams, everything arrives from the polled document. Its failure at boot was silent in three parts. The first sync failed and logged a warning, keeping the "current" set — which was empty. `/health` computed readiness from probeable upstreams alone, and with zero of them `healthy == probeable` held vacuously, so the pod answered `200 ok`, passed its readiness probe, and joined the Service. Every `tools/list` then fanned out to nothing and returned an empty list with no error, because an empty fan-out has no partial failure to report. The pod recovered on the next successful poll and nothing in the interval said anything was wrong — `fold_discovery_syncs_total{outcome="error"}` made it alertable, but nothing made it *unready*, and unready is what keeps a pod serving empty lists out of rotation.

  `/health` now answers `503` on a gateway with no upstreams whose discovery source has never been applied, and carries a `discovery` object (`lastOutcome`, `lastSyncAt`, `applied`) saying why — the response shape is frozen additive, so the new field is within the contract, and `fold --healthcheck` treats any answer as alive, so the container check is unaffected. The condition is *never applied*, not *currently failing*: a source that goes down after a document has been applied keeps the last good set serving, as it always did, and a source that applies an **empty** document is `200` because the registry said the federation is empty and fold believes it. One consequence is written into the deploy guide rather than smoothed over: the startup probe's budget now also bounds how long a discovery-only pod's source may be down at boot before the pod is restarted, and a federation whose registry comes up slowly should raise it.

- **The chart promised zero-downtime rollouts and had none of the parts.** `docs/deploy.md` said "zero downtime with `replicaCount` ≥ 2 and the PDB", and the mechanism was incomplete in three places. The Deployment had no `strategy`, so Kubernetes' 25%/25% defaults let a two-replica rollout run on one pod — which a PDB of `minAvailable: 1` permits. There was no `preStop`, so SIGTERM closed the listener the instant it landed while endpoint removal was still propagating to kube-proxy and the ingress, a window of refused connections on every pod of every rollout. And nothing tied the three timers together: `terminationGracePeriodSeconds: 30` was chosen around a 10 s drain that was hardcoded in the binary. Chart **0.4.0** ships `strategy: maxUnavailable 0 / maxSurge 1`, a `preStop` sleep (the Kubernetes 1.30+ `sleep` action — the image is distroless and has nothing to sleep with — omitted on older clusters), `server.drainTimeout` wired to fold's new `--drain-timeout` and rendered only when set so an older image never sees a flag it does not know, and a render-time guard that refuses a grace period that does not exceed sleep plus drain. `revisionHistoryLimit` and `priorityClassName` land alongside, and the HPA gains a `behavior` block whose default scales down slowly, because scale-down cuts the SSE sessions on the pods it removes.

  **Readiness on `/health` removes every pod from the Service when every upstream is down**, turning fold's own answer — `-31041`, or a list with a `partialFailure` marker — into an ingress 502 from a Service with no endpoints. That is documented intent and stays the default; what was missing was any way to choose otherwise, since `probes.readiness` exposed no path. `probes.readiness.mode: tcp` keeps pods in rotation on process liveness, `probes.readiness.path` covers the rest, and the deploy guide states the trade in both directions rather than picking one silently.

  **`existingConfigMap` with the metrics listener produced a dead port.** The chart injects `server.metricsAddr` only into an inline `config`; with an operator-managed ConfigMap it still opened containerPort 9090, the Service port, the NetworkPolicy rule, and the ServiceMonitor target, and the gateway never bound it — a scrape target down with no other symptom, in a chart whose every other footgun has a `fail` guard. It has one now, lifted by `metrics.listener.externalConfigSetsMetricsAddr: true` when the operator's document really does set it.

  **There was no way to trust a private CA.** The gateway has no CA config, the chart had no volume hooks, and no document mentioned `SSL_CERT_FILE` — an internal-PKI shop whose upstreams, IdP, or audit webhook sit behind its own CA could not install without forking the chart or the image. `extraVolumes` / `extraVolumeMounts` are the chart half; the deploy guide's new "Private CAs" section is the other, and it says why there is deliberately no `caFile` field: Go already reads `SSL_CERT_FILE` and `SSL_CERT_DIR`, and a config field would duplicate that inside the frozen surface. The same mounts are what make the `file` audit sink and a `deadLetterPath` usable under `readOnlyRootFilesystem`, which nothing had pointed out either.

- **`audit.scrub.redactUsageKeys` was redacting the client's response, not just the trail.** The `usage` map on an audit event is the upstream's own result `_meta.usage` — the gateway stores a pointer to it when the result comes back, hands the event to audit, and *then* serializes that same result to the caller. The scrub deleted keys from that map in place, so a control introduced to keep secrets out of the sinks was quietly taking fields away from the response, and the invisibility rule was broken in the one place a redaction feature is most likely to be turned on. The existing test built an isolated event and could not see it. The scrub now edits a copy; `gateway/auditscrub_test.go` calls a real upstream through fold with the scrub configured and asserts the client still has the key and the file sink does not.

- **The default audit sink wrote synchronously on the request goroutine.** `stdout` is the sink the quick start uses and the one most likely to be a pipe somebody else reads — a container log driver, a collector — and a pipe nobody is reading blocks its writer, under a mutex, for every request in the process. The webhook and OTLP sinks had always refused to be the reason a request is slow; `stdout` now refuses the same way, from a worker behind the same 1024-event buffer, dropping and counting on overflow (`fold_audit_events_total{sink="stdout",outcome="dropped"}` — a new label value on an existing metric, which the compatibility contract allows) and reporting `delivered` like the file sink already did. The `file` sink stays synchronous **on purpose**: it is the durability anchor `requireDurable` points at, and a buffered file would make that promise conditional on a clean shutdown. The configuration reference said delivery was asynchronous for every sink; it now says which.

- **A closing webhook sink abandoned its buffer, uncounted.** `Close` stopped the delivery worker and released the dead-letter file with up to 1024 events still queued and, worse, with a batch that had been mid-retry when shutdown arrived leaving the worker with no accounting at all — exactly at the moment a rolling restart makes the tail of the trail interesting, and in direct contradiction of the contract that a lost event is always countable. A closing sink now drains: each buffered batch gets one attempt inside a three-second bound, a post that was already in flight is aborted when that bound is spent rather than being allowed the client's full timeout, and whatever cannot be placed is dead-lettered where there is a `deadLetterPath` and counted as `dropped` where there is not. `stdout` closes the same way, counting what a wedged writer kept, including the event stuck inside the write.

- **A key the IdP revoked kept verifying tokens for the life of the process.** The JWKS cache declared a five-minute TTL, assigned it, and never read it: the only thing that prompted a refetch was a token presenting a `kid` the cached set did not have. That handles rotation-*in* — a new key appears, tokens start naming it, fold fetches — and it handles nothing about rotation-*out*. An identity provider that withdraws a compromised key does not send a notification; it stops publishing the key, and the tokens that were signed with it keep arriving with the same `kid` they always had. fold answered every one of them from the stale set. Rotation-in was tested; revocation was not, and `unused` did not flag the field because it is a struct member rather than a symbol. The cache now refreshes a set once it is older than the TTL regardless of what the token presents, single-flighted on the same per-URI gate as before, so `auth/auth_test.go` can revoke a key, advance the clock six minutes, and watch the token it signed stop verifying.

- **Four unsafe postures the gateway accepted silently now say so at startup, and one of them is closed.** fold's defaults are safe by *pairing*: auth is off out of the box because the listener binds loopback, and the quick start works with no IdP because nothing off the machine can reach it. Nothing checked the pair. `--host 0.0.0.0` on a config with no `auth` section was an open gateway whose only sign was an Info field reading `authRequired=false`, and it compounded: `/health`'s redaction of URLs, owners, and raw connect errors was gated on auth being *on*, so the same command published every upstream URL and every error string — which can name secret env vars — to anyone who could reach the port. `/health` is now redacted for every caller, whatever the auth mode; it is unauthenticated by design, and the detailed view belongs to `/api/federation`, which authenticates. The pair itself is now checked: auth off on a non-loopback bind logs a warning naming the exposure.

  Three more warnings, each for a posture validation accepts on purpose. A **credentialed upstream at `http://`** — `static`, `passthrough`, `token-exchange`, `client-credentials` — sends its credential, or the caller's own bearer token, in the clear; validation forces `https` onto every other place a credential travels and deliberately not here, because cleartext inside a mesh that encrypts the hop is a legitimate topology fold cannot tell from a mistake. Each such upstream is now named at startup (loopback exempt), and the security model records it as an accepted risk in those words. **EMA with neither `allowedAssertionTypes` nor `allowedClientIds`** — the allowlists v1.15.0's token-endpoint hardening added — still exchanges any correctly addressed IdP-signed JWT, exactly as `auth/ema.go` says in plain language; it now says so in the log too, mirroring what discovery has always done for its missing allowlists. And an **absent `policy` block** is an allow-all engine, which the deploy checklist stated and `docs/defaults.md` and README did not: README billed deny-by-default in three places without the qualifier, and the defaults review had no row for `policy` at all. Both now say what the code does. The four warnings are listed together under "Log streams" in the operations guide, so a hardened deployment can be checked by grepping for none of them.

- **Two host allowlists each left one door unchecked.** Both are additive fields; both defaults are unchanged; both gaps are now warned about at startup when the field is absent.

  **`allowedHosts: ["*"]` switched Origin validation off with it.** The Host and Origin checks lived inside one `if !wildcard`, on the reasoning that a deployment behind a proxy that validates Host has nothing left to check. MCP disagrees: the Origin check is what defends against DNS rebinding, and it is required however Host is handled. The obvious fix — require same-origin under the wildcard — would refuse the browser clients that work today, Inspector on `localhost:6274` against a `["*"]` gateway among them, and a changed meaning is what the compatibility contract forbids. So the rule becomes explicit instead: **`server.allowedOrigins`** names the Origins browser clients legitimately use (exact hostnames or `*.suffix`, matched against the Origin's host), applies on its own whatever `allowedHosts` says, and `["*"]` is the explicit any-origin form for an operator who accepts the exposure. Absent, the old derivation from `allowedHosts` stands — and a Host wildcard with no `allowedOrigins` is named in the startup log rather than inherited silently. Requests with no Origin, which is every non-browser client, are unaffected either way.

  **Discovery bounded where a secret could travel and not where an upstream could live.** `allowedCredentialHosts` applies only to credentialed entries, and the exposure it closes — a compromised source pointing a gateway-held secret at a host of its choosing — is real. But a source needs no secret to register an upstream at an arbitrary host, and doing so puts that host's tool names and descriptions, the instruction set a model acts on, into every caller's `tools/list`, with the gateway dialing the host on every fan-out. **`discovery.allowedUpstreamHosts`** bounds every discovered endpoint host, credentialed or not, with the same pattern rules and the same whole-document rejection as the other three; the chart's `NOTES.txt` and the deploy checklist list it beside them. A document with one disallowed host is rejected whole — the compliant sibling entry is not applied either — which is the discovery path's posture everywhere and is pinned by test.

- **Four ways one caller or one upstream could cost the whole process.** None of them a crash in the ordinary run; each a bound that was missing.

  **A body that never finished held a connection forever.** `ReadHeaderTimeout` bounds the headers and a `WriteTimeout` is off the table because MCP responses are streams, so a client that sent its headers and then dribbled one byte a minute of a sub-cap body held a connection and a goroutine indefinitely — `MaxBytesReader` bounds size, not time. A 30-second read deadline now covers the body: armed when a body-bearing request enters, lifted the moment the body reaches EOF (and again when the handler returns), so it bounds the *request* and never the response. That property holds because every handler fold mounts reads its body to EOF before answering — the SDK uses `io.ReadAll`, the token endpoint parses a form — and it is pinned by a test that runs a one-second tool call under a 200 ms deadline and expects it to succeed.

  **A panic in a plain HTTP handler was invisible.** `net/http` recovers a handler panic per connection, so the process survived, but it recovered into its own logger: not counted in `fold_panics_total`, no audit event, no slog line. Every handler outside the MCP dispatch was in that position — `/health`, `/icons`, the well-known documents, and `/oauth/token`, which is unauthenticated — so an operator paging on the panic counter, as the dashboard recommends, would have seen nothing while an open endpoint panicked on every request. A recover middleware now sits inside the body cap and outside the mux, counting under site `http`, emitting one audit event, and answering 500 when nothing has been written yet. It is deliberately not the outer recover `rescue.go` warns against: the MCP path's boundary stays where it was, below the SDK's dispatch, where audit can still see the request.

  **The subscription table was unbounded under passthrough.** It is keyed by a URI the caller chose, and under passthrough any URI resolves to the one upstream, so a single long-lived session could grow it without limit — the one per-caller map not behind `internal/bounded`, and for a reason: evicting an entry would orphan the upstream subscription behind it and break the ref-count every other subscriber depends on. The bound is a refusal instead. A session may hold at most 1024 subscriptions; the next is refused with `-32602` (a parameter the caller can change by unsubscribing, which is what that code already means for cursors — the frozen minted codes gain nothing) and the slot is back the moment one is released. Re-subscribing to a URI a session already holds is not a new subscription and is never refused.

  **`fold-stdio` had no panic containment at all.** The gateway recovers on thirteen goroutine sites with a metric and a stack trace; the shim recovered on none, so a panic in the sweeper, a pump, the stderr relay, or a probe ended the process and took every bridged stdio server with it. Each site now runs under a `rescue` mirroring the gateway's — a pump that panics still tears its own session down, a probe that panics still answers, as a failure rather than a swallowed "healthy" — counted in `Stats.Panics`, surfaced on the shim's `/health`, and exported as `fold_stdio_panics_total`.

- **An upstream's icons were unreachable through the gateway, and nothing said so.** MCP lets a server hang an icon off a tool, prompt, or resource, and it tells the *client* how to handle one: fetch only `https` or `data:`, reject unsafe schemes and cross-origin redirects, fetch without credentials, treat the declared MIME type as advisory and detect the real one from the bytes — and "verify that icon URIs are from the same origin as the server". Behind a gateway that last rule is decisive. An upstream's icon points at the *upstream's* origin, which is neither the origin the client connected to nor, for the cluster-internal upstream that is the ordinary enterprise case, an origin the client can reach at all. So a conforming client rejected every federated icon and a lenient one failed to load it, and fold looked like a server whose upstreams have no icons — the invisibility rule broken in the direction nobody reports, because there is no error to report.

  The string `icon` appeared nowhere in fold: not in the code, not in the config schema, not in README "Not implemented". They survived federation at all only by accident, because `namespacedTools` and its peers take a shallow struct copy and overwrite the one field they rewrite, so a field fold has never heard of rides along.

  fold now mints `{server.publicUrl}/icons/{namespace}/{digest}` and serves the bytes. It is the move v1.14.0 made for MCP Apps `ui://` URIs and it is safe for the same reason: an icon `src` is republished on every list rather than persisted by a client, so rewriting it costs nothing a client relies on. Resolution comes from the URL itself — the namespace names the upstream, the digest indexes its own list — so there is no global index and no probe, and a digest evicted from the bounded index is rebuilt from the cached list rather than lost.

  **Four bounds keep it from being an open proxy**, and they are the feature. Only an icon whose host is one of *that upstream's own configured endpoint hosts* is minted — the same bound credential attachment uses, "nothing rides to a host the upstream did not configure" — checked when the URL is minted and again immediately before the fetch, so a hand-built digest cannot aim the gateway at a metadata service. An icon on any other host is republished exactly as sent: it is already a public URL, and withholding it would only take an icon away from a client lenient enough to have rendered it. Unsafe schemes (`javascript:`, `file:`, `ftp:`, `ws:`) are dropped rather than republished, which is the one place this removes data — a client MUST reject them anyway, so dropping costs a conforming client nothing and avoids fold putting its own name on one. `data:` URIs pass through untouched. And passthrough mints nothing, exactly as it rewrites nothing else.

  The fetch carries **no credentials by construction rather than by policy**: the client that performs it has a plain transport, so there is no code path from an icon fetch to `auth.UpstreamCredentials` at all. It refuses redirects outright — a redirect is never a legitimate step in fetching an icon, and allowing even a same-host one reopens the origin question. It is bounded by `server.icons.maxBytes` (256 KiB) and **refuses rather than truncates**, because half an image is a response the upstream never sent. Concurrent requests for one icon collapse to one upstream fetch, so a page of `<img>` tags is not a load amplifier.

  **`image/svg+xml` is refused**, and the reasoning is on record rather than implied. Two arguments, either sufficient. fold would be serving the SVG from *fold's own origin*, where an SVG's embedded script runs same-origin with `/console/`, `/api/federation`, and `/oauth/token` — strictly worse than the upstream serving it, since the upstream's origin holds nothing of fold's. And structurally: SVG is XML and has no magic bytes, so the strict magic-byte allowlist the specification asks a consumer to maintain cannot admit it without either trusting the declared content type or parsing the XML, and the second is the inline content inspection the roadmap declines. The allowlist is `image/png`, `image/jpeg`, `image/webp`, `image/gif`.

  **The endpoint is unauthenticated, and that is forced rather than chosen.** The specification has clients fetch icons without credentials and a browser `<img>` carries no bearer token, so an authenticated endpoint would serve nothing to the clients it exists for. What it discloses is bounded to match: the path names no tool, prompt, or resource — only a namespace and a digest — and the bytes are branding artwork identical for every caller, the same class as the console's static assets. One limit is stated rather than implied, in README and in the security model: **policy filtering is preserved here by unguessability, not by authentication.** A principal who cannot see a tool is never handed its icon URL, but one who guesses a URL gets the bytes. `server.icons.enabled: false` is the switch for an operator who does not accept that; an HMAC-keyed digest would make the URL a true capability and is named as the upgrade path rather than built, because it needs a fleet-stable secret most deployments do not configure.

  Three new fields, all additive. **`server.publicUrl`** is the absolute origin clients reach the gateway at, falling back to `auth.resource`; with neither, nothing is minted and icons are served exactly as the upstream published them, which is what fold did before this existed, plus one startup log line naming the fix. fold cannot infer it — it terminates no TLS of its own and reads no forwarded-proto header — and a `Host` taken from the request cannot stand in, because `allowedHosts: ["*"]` is a supported posture behind a trusted proxy and a caller-supplied `Host` would then be injected into every URL fold mints for that caller. It is also what lets the rewrite live inside the existing `publicView` memo: the benchmark is allocation-identical to before this change at every federation size, because a minted list is computed once per cache generation rather than once per request. **`server.icons`** carries the switch and the three bounds. **`server.identity`** adds fold's own `websiteUrl` and `icons` to what it reports at `initialize` — not proxied, since an operator sets a URL they own, and `data:` is recommended for exactly the same same-origin reason this whole entry is about.

  Three narrower gaps are documented rather than closed: SVG, resource-template icons, and passthrough.

- **Two canaries, for the class of bug that let icons go unnoticed.** Fold's list egress carries every field the SDK models forward for one reason — a shallow struct copy — and nothing enumerated the rest. That is what makes it correct and what makes it fragile, and it is not hypothetical: v1.15.0 fixed exactly this shape, where three sites rebuilt request params and silently dropped `inputResponses` and `requestState`. `gateway/egressdrift_test.go` now asserts the property directly. A fully-populated fixture is fetched twice — once from the upstream, once through fold — and the marshalled JSON is diffed; the only tolerated differences are a short declared allowlist (`name`, `_meta.ui.resourceUri`, a `ui://` `uri`), and widening it is a code review. The comparison is over JSON rather than Go values because the wire is what the invisibility rule is about, and because `Tool.InputSchema` is `any` — `json.RawMessage` on one side, `map[string]any` on the other. Reflection appears in one narrow role: a diff cannot notice a field *neither* side populates, and a field neither side populates is precisely how icons could have been dropped with every other test green.

  `gateway/mergeorder_test.go` pins that a federated list merges in configuration order. That was already true — `fanOut` writes `results[i]` by upstream index rather than appending on completion — but nothing tested it deterministically: the existing paginated-walk test would have failed only *sometimes* under a completion-ordered merge, which is the worst kind of coverage. The new test chains its upstreams so the last in configuration order always answers first, with no sleeps and no timing assumption. This matters beyond the `2026-07-28` revision's "SHOULD return tools in a deterministic order": fold's cursors are offsets into the merged snapshot, fingerprinted by the sequence of names, so a merge that varied with completion would either refuse every continuation or serve a window into a differently ordered list. The partial-failure halves are pinned too — a cursor minted before an upstream died is refused rather than silently shifted, and one whose dead upstream contributed nothing visible keeps working.

## v1.15.0 — 2026-08-25

An audit against the specification, and the breaking change it forced.

- **Every error code fold mints has changed, because the protocol reserved the range they were in.** The `2026-07-28` revision partitioned the JSON-RPC server-error space: `-32020`–`-32099` is "reserved for the MCP specification", which implementations "**MUST NOT** emit ... [any code] that is not defined by this specification", and `-32000`–`-32019` is legacy, where "new codes **MUST NOT** be allocated". fold minted five codes in the middle of the reserved band and one in the legacy band. The specification's own instruction is to allocate outside the reserved range entirely, and that is what these now do — only the thousands digit moved, so the mapping is mechanical: `-32040`→`-31040` (upstream rate limit), `-32041`→`-31041` (upstream unavailable), `-32042`→`-31042` (policy denied), `-32043`→`-31043` (unknown namespace), `-32044`→`-31044` (budget exhausted), and `-32002`→`-31045` (task owned by no upstream).

  **`-32042` is why this could not wait for a major version.** The specification has already given it a meaning — "URL elicitation required" — and the SDK fold links against acts on it: it parses elicitations out of the error, invokes the client's elicitation handler, and *retries the call*. A fold policy denial reaching such a client is therefore not read as a denial at all; the user is prompted for an out-of-band interaction that does not exist and the refused call is tried again. A deny-by-default gateway whose refusals turn into prompts and retries is not a cosmetic conformance gap. `-32002` was wrong in a quieter way: the revision defines it as "resource not found" and tells clients to keep honouring it from older servers, so an unowned *task* id read as a missing *resource*.

  Minted error codes are frozen by the [v1 contract](README.md#api-stability), and this breaks that freeze in a minor. It is the same trade v1.9.0 took and for the same stated reason — there are no users to protect yet, and taking the break now rather than after launch is the honest choice. Anything matching on fold's codes needs the substitution above; nothing else about the errors changed, including their messages, their `data`, and the audit outcomes they map to.

- **The gateway can keep its own streams alive.** MCP's expectation is that a *client* pings if it wants a session kept alive — reasonable advice to a server, awkward advice to a gateway, because the idle timeout cutting the stream usually belongs to a load balancer the operator configured and the gateway is often the only thing in that path they control. A cut stream was survivable (both ends reconnect with backoff and `Last-Event-ID`) but meant reconnect churn and a window with no notifications delivered. `server.keepAliveMs` sends the pings from fold's side; absent, it is off, which is what fold has always done.

  Enabling it is not free, and the three ways it is not are measured rather than reasoned about, because two of them change a working deployment. **It disconnects clients that decline the standalone SSE stream** — a server-to-client ping needs that stream to land on, the transport makes it a MAY, and a `POST`-only client is correct, healthy, and unreachable by a ping; measured, such a client is closed after three ticks and answered `session not found` on its next call. **The interval must clear twice the slowest legitimate round trip**, because each ping is given half the interval to be answered, so a slower client burns a failure every tick. And **it supersedes `sessionIdleTimeoutMs` for any client that answers**: a ping is answered with a `POST`, and a `POST` is what resets the idle timer, so fold's own keepalive keeps alive the session it is pinging — measured at a 250 ms idle timeout against a 50 ms keepalive, still alive after 1.8 s having sent nothing. What changes is the criterion, not the setting: reclamation moves from activity to liveness, so a departed client goes *faster* (three misses rather than the whole timeout) and a present-but-idle one never goes at all.

  fold tolerates three consecutive misses rather than the one the SDK defaults to, because a gateway's clients sit behind whatever network an operator has and the specification's own guidance is that *multiple* failed pings may trigger a reset. And `ping` is a method the `2026-07-28` revision removed, so this joins the list of things correct for the era fold serves with no counterpart in the next.

- **A routing header the caller sent stopped at the gateway.** MCP lets a client mirror selected tool arguments into `Mcp-Param-{Name}` headers so an intermediary can route on them without parsing the JSON-RPC body, and the transport addresses intermediaries by name: one that does not recognize such a header "**MUST** forward it and otherwise ignore it". fold is that intermediary and dropped them — its upstream leg is a fresh SDK client session whose headers the SDK generates, so nothing the caller set survived the hop, and an upstream fronted by a header-routing balancer would never see what it was routing on. They are now relayed.

  Both halves of the sentence are implemented. fold forwards them and **ignores** them: it does not read the values, does not route on them, and lets nothing they contain influence a decision, so the body remains the only thing fold parses and the headers stay a hint rather than a second, forgeable control surface. The relay is also deliberately the narrowest thing that satisfies the rule — fold does not forward arbitrary client headers, which is a standing design decision and the reason a caller cannot smuggle a credential or an identity assertion to an upstream through one. This is the single namespace a specification requires be passed through, it never overwrites a value the SDK generated for the call fold is actually making — that value is the one guaranteed to agree with the body, which is what the specification actually requires — and it sits inside the same host bound as credential attachment, so nothing caller-supplied rides a request to a host the upstream did not configure.

  One consequence is documented rather than smoothed over, because "fold ignores them" is true of fold and not of the deployment: a server validates a param header against the body only once it has negotiated `2026-07-28`, and fold's default upstream protocol sits below that so the sessionful handshake can carry server-initiated traffic. On a default deployment, then, nothing validates these — an upstream that routes on one must check it against the body itself. They also ride every request of the call that carried them, including that session's own handshake, so a value scoped to one invocation can reach a router deciding where a whole session lives. Both are in README beside the feature.

- **The protocol-era transition is now instrumented and written down rather than assumed.** fold serves the handshake era; the `2026-07-28` era is unreachable through it, because the SDK's streamable handler serves that revision only on stateless HTTP servers and fold runs stateful for session-keyed bridging. That was already noted for `subscriptions/listen`, and `gateway/listen_test.go` pinned it from the client side — that a default-options SDK client falls back. A client is free not to be the SDK, so `gateway/era_test.go` now pins the server side too: a raw request declaring the era, by header or by per-request `_meta`, must be refused rather than served. It deliberately does not pin *how* it is refused — v1.7.0 answers an HTTP 400 and the SDK's main branch returns a JSON-RPC error instead, and a canary that asserted the status would fail on that bump for a reason nobody cares about. Being served is the drift; the shape of the refusal is not.

  README "Not implemented" gains two entries in the same pass. One collects what the new era changes and fold has not done — no advertised `extensions`, so a client following the tasks extension's negotiation would never reach fold's federated tasks; `tasks/list` and `tasks/result` federated though the redesigned extension removed them; `resources/subscribe` advertised and `logging/setLevel` handled though the revision retired both; and relayed results carrying no `resultType` of their own. The other records that an upstream's own `ttlMs` and `cacheScope` are not honoured, which is structural rather than an oversight: the SDK's paginating iterators consume the envelope those hints ride on, and `state.ListCache.GetOrFill` takes its TTL before the fill that would produce one. And `docs/roadmap.md` gains a deprecation table — sampling, roots, logging, and RFC 7591 dynamic client registration all carry an earliest removal of the first revision on or after 2027-07-28, which nothing in fold's documentation previously mentioned. The DCR row cuts against a plan rather than an implementation: Horizon 3 holds it as demand-gated, and building it now would be adopting something new implementations are told not to.

  [Roadmap](docs/roadmap.md) item 13 is corrected in the same pass. It plans to govern server-initiated requests, and the `2026-07-28` revision *removed* that mechanism — a server "MUST send server-to-client requests ... using the MRTR pattern. The previous pattern of server-initiated requests is no longer supported." The governance surface survives and its call site moves: under multi-round trip an upstream returns an input-required result rather than asking, so what the item governs is an inspection of `inputRequests` in a relayed result, not a handler on a bridged session. The per-request handler check that design record argues for as the boundary has no meaning there. Sampling and roots carry an additional deprecation with an earliest removal of the first revision on or after 2027-07-28, which the roadmap did not mention at all. The bridged-session apparatus is recorded as what it is — a legacy-era compatibility layer, valuable for as long as handshake clients exist, and not the shape of what replaces it.

- **A retry that answered an upstream's question arrived looking like a first attempt.** MCP's multi-round-trip pattern has a server return an `InputRequiredResult` carrying the questions it needs answered and an opaque `requestState`; the client replies by retrying the *original* request with `inputResponses` filled in and that state echoed back. The specification is emphatic about the echo — a client "**MUST** echo back the exact value" and "**MUST NOT** inspect, parse, modify, or make any assumptions about" it — because the pattern is otherwise stateless and that field is the only thing carrying the server's context across the round trip. fold rebuilt request params at three sites (`tools/call`, `prompts/get`, and the minted-`ui://` branch of `resources/read`) and silently dropped both fields. The upstream therefore saw a first attempt every time, asked its question again, and the SDK's client retried — to its ten-attempt ceiling, re-prompting a human on each pass. Both fields are now forwarded unchanged. The other two `resources/read` branches were always correct, because they forward the params they were given rather than building new ones; that is the difference the fix is about. Note what this does *not* change: fold's upstream client runs the SDK's multi-round-trip middleware, so in the ordinary case fold answers an upstream's question from the caller's bridged session and retries below the router rather than relaying the question outward. The forwarding fixed here is the path a downstream client that speaks the pattern itself takes. README "Not implemented" now records the termination behaviour and its three consequences.

- **A client had to be refused before it could learn which scopes it needed.** fold's protected-resource metadata named the authorization server but not the scopes, so a client's only route to the requirement was to authorize with whatever it guessed, connect, call a tool, and read the answer out of the denial. `scopes_supported` is now published in that document — every scope `policy.rules[].subjects.scopes` names, deduplicated and sorted so the document is stable between fetches — which is the field [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) §2 recommends for exactly this. It is a hint rather than a contract: holding every scope listed entitles a caller to nothing by itself, since scopes are one gate among several. The document is now built per request rather than once at startup, because policy hot-reloads and a construction-time copy would have gone on advertising the rules fold started with.

- **Every federated list went out with an invalid cache scope.** MCP's caching rules define `cacheScope` as exactly two values, `"public"` or `"private"`, and require the hint on every complete list result. fold builds its list results itself — federated, merged, and filtered per principal — so they never reach the SDK handlers that fill those fields in for an ordinary server, and every `tools/list`, `prompts/list`, `resources/list`, and `resources/templates/list` was answered with `"cacheScope": ""`. That is neither permitted value. It never became an incident because the accompanying `ttlMs` is `0` — the spec's "immediately stale" — so a conforming client re-fetches regardless; but the two hints disagreed, and the one that would have contained the damage was the one fold was not setting. A client applying the documented "absent means public" default to an empty string would have treated a list fold had filtered *per principal* as shareable with anyone, which is the specification's own example of what must be private. fold now computes the scope from the configuration, once per routing snapshot: `"private"` whenever two callers can legitimately receive different lists — any policy rule, any tenant, or any upstream whose credential is caller-derived — and `"public"` only for a federation that serves one list to everyone. `ttlMs` stays `0` deliberately, because a reload, a discovery sync, or a policy change can alter what a caller may see at any moment, and picking a lifetime here would pick it for every deployment at once.

Three things a gateway must not let past it, and a policy that can finally say "requires the write scope".

- **Policy and tenant selectors match on OAuth scopes, and a scope denial says what would fix it.** fold could not express the most ordinary enterprise authorization predicate there is. Scopes arrive in the `scope` claim as a *space-delimited string* (RFC 6749), and the claims matcher compares whole values — so `claims: {"scope": "write"}` simply does not match a token carrying `read write admin`, and no amount of writing it differently helped. `subjects.scopes` reads `scope` or `scp`, as a string or an array, and matches **conjunctively**: every scope named must be held. That is deliberately unlike `subs` and `groups`, which are alternatives, because those answer *who is this* — where one identity is enough — while a scope answers *what were they granted*, where a list is a set of requirements. It gates like `claims` do: combine it with an identity, or let it stand alone. The same field works in `tenants` selectors. When a caller is refused and scopes were the *only* obstacle, `-31042` now names them in the message and in `data.missingScopes`, and the audit event carries them, so an agent re-authorizes for what it lacks instead of retrying blind. Two disclosure rules bound that: only scopes the caller lacks appear, since re-authorizing accumulates rather than replaces; and a rule contributes only when it targets that exact invocation, because naming a requirement that guards something the caller could not reach anyway would disclose that it exists. Documents naming no scopes evaluate exactly as before, and the list path never computes a shortfall at all.

- **A caller could tell an upstream what protocol version, client identity, and capabilities it was talking to.** The MCP `_meta` map carries connection-owned keys — `io.modelcontextprotocol/protocolVersion`, `/clientInfo`, `/clientCapabilities` — and fold forwarded a request's `_meta` to the upstream unchanged. Those keys describe the connection a request arrived on, and behind a gateway there are two: the caller's, and the one fold holds. The SDK makes the mismatch consequential in both directions, filling them on an outgoing request only when they are *absent* and, on the receiving side, preferring a request's `_meta` to the session's own initialize params — so a value forwarded from the caller wins over the one fold negotiated, and the upstream believes it. fold already refused to relay a client's raw declaration at initialize, where the capability profile is computed from the extension identifiers fold implements rather than from the map the client sent; this is the same argument on the per-request path, which that guard did not cover. All four typed forwarding paths and the opaque task-params path now strip them, and an upstream's `serverInfo` is stripped in the reverse direction, where leaving it in place both reached the caller and suppressed fold's own identity. Every other key — progress tokens, trace context, task and app metadata, vendor keys — is untouched. On the current protocol era only a hand-rolled client can set these; on `2026-07-28` every request carries them, so this is a prerequisite rather than a hardening.

- **EMA advertised an authorization server that answered 404.** With the embedded token endpoint enabled, fold names itself in `authorization_servers` in its RFC 9728 protected-resource metadata — and then served no RFC 8414 document, so a client that followed the pointer found nothing and every operator had to configure the token endpoint out of band. The document is now published at `/.well-known/oauth-authorization-server`, and at the RFC 8414 §3.1 path-scoped form as well when `auth.resource` carries a path, since that is where a conforming client looks. Endpoints are derived from the issuer's origin rather than concatenated onto it: a canonical MCP resource identifier commonly includes a path, and `…/mcp/oauth/token` is not where fold serves anything. Assertions typed as OAuth access tokens (`at+jwt`, RFC 9068) are now refused at the token endpoint — nothing legitimately presented as an identity assertion carries that type, and accepting them let a token minted for the gateway's audience be redeemed as a grant.

- **Nothing bounded what an upstream could return.** `server.maxBodyBytes` has capped the inbound direction since v1, and every other thing fold fetches — tokens, JWKS, the discovery document, the decision hook — carries its own limit; the upstream data path had none, so a buggy or hostile upstream could spend the gateway's memory by answering a list with more of it than the process has, decoded and then cached, and with `server.redisUrl` set pushed into shared fleet state. `upstreams[].maxResponseBytes` bounds it, defaulting to 64 MiB — far above any real payload, because this is a backstop rather than a size policy — with negative restoring the old behaviour. It refuses rather than truncates: a shortened body would be a response the upstream never sent, so the call fails with `-31041` and nothing partial is served or cached. On an event stream the bound applies per event rather than per connection, since a subscription that stays open for a day is legitimately unbounded in total. A value below 64 KiB is refused at startup, because every call failing and the breaker opening does not read as a typo.

## v1.14.0 — 2026-08-15

Interactive apps survive the trip through the gateway.

- **An MCP App's interface belongs to the upstream that published it.** [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) (SEP-1865) points a tool at an interactive interface through a `ui://` resource URI in its `_meta.ui` — a URI the extension requires to be unique only *within one server*, and which the published starter templates ship with no server segment at all. Federate two upstreams built from one template and they advertise the same URI for two different interfaces: fold served a read of it from whichever upstream listed it last, so a host rendering one team's tool could get another team's app, and which one it got depended on request history — a cold gateway answered from the probe order, a warmed one from the list. Those URIs are now minted per namespace as `ui://fold/{namespace}/{rest}` in `_meta.ui` (both the nested and the deprecated flat form), in `resources/list`, in what a read answers with, and in `resources/updated` for a subscribed interface; reads resolve straight to the owner, with no probe and no dependence on what some other client did first. This is the one exception to fold never rewriting a resource URI, and it is a narrow one: only the `ui://` scheme, a form derived from the namespace the operator already chose, policy and audit still deciding on the URI the upstream published, and passthrough rewriting nothing. A `ui://` URI embedded in a *tool result* is deliberately not chased, because following it there is response-body rewriting.
- **A client's rendering declaration now reaches the upstream.** MCP Apps is negotiated by the client — a server checks `capabilities.extensions["io.modelcontextprotocol/ui"]` before registering UI-enabled tools and serves a text-only fallback to anyone who did not declare it — and fold declared nothing at all, on every session, for every caller. A host that asked fold for apps was served the fallback, which is the invisibility rule broken in the direction nobody reports, because the gateway simply looks like a server whose upstreams have no apps. fold carries the declaration instead of configuring it: a named invocation rides the per-client session, which declares what its client declared, and lists ride root sessions keyed by a normalized capability profile — one session per upstream where every client is alike, exactly as before, two where they are not, and neither client ever served the other's list. There is no config field and deliberately not even an opt-out: an operator who does not want an upstream's app variants is expressing a policy, and a handshake setting that works by misreporting the client would be a control with the wrong name. The profile is computed from the extension identifiers fold implements rather than from the client's raw map, so a caller declaring invented extension ids cannot mint sessions or cache entries; it also qualifies the list-cache key, which reaches Redis, where a profile-blind key would let one instance's app-aware list be served to another instance's plain client.
- Two gaps remain and belong to the extension rather than to fold, both now on record upstream: an app that hardcodes a tool name cannot call it once federation has namespaced it, and the host's rule that an app may not call tools across servers has no meaning when every upstream arrives on one connection, because nothing on the wire distinguishes an app-initiated `tools/call` from a model-initiated one. Reasoning, the wire evidence behind both, and the designs that were rejected on the way: [docs/design-mcp-apps.md](docs/design-mcp-apps.md).
- **The embedded console leads with what is wrong.** An operator arrives at `/console/` with one question — is the federation healthy, and if not which upstream — and the page answered it with a count inside a card, leaving them to reach the upstream list and work out the filter for themselves. Overview now opens with the condition in a sentence and a link to the list already filtered to it, and renders nothing at all when the federation is healthy, because a banner that is always present is furniture. It deliberately does not announce itself as an alert: that is reserved for the console being degraded — unauthorized, version skew, a failed read — rather than for the answer somebody navigated in to read. Ctrl/Cmd-K now jumps to a route, an upstream, or one of the several hundred names a real federation puts in the catalogue. The four embedded font subsets are rebuilt in this release too, cut from upstream releases pinned by tag and sha256 rather than from the previously-shipped bytes, so what every fold binary embeds has a provenance that can be checked instead of one that circles back on itself; the console's own suite also now runs axe over every route. Vendored from `fold-run/fold-console` at `31c31ab`.

## v1.13.0 — 2026-08-14

An audit sink that authenticates no longer forces its token into the config.

- **A webhook audit sink can take its bearer token by reference.** `headers` accepts static values only, so a receiver that authenticates left the operator writing the credential into the config document itself — which made that document the one part of a fold deployment that could not be checked into a repository, printed in a log, or handed to somebody debugging a federation. `discovery` and the external decision hook have both taken a `bearerSecretRef` since they existed; the audit sink is the third feature that makes outbound requests and was the only one without it, while the `AuditSink` struct's own comment pointed at the convention it could not use. Two things are refused rather than reconciled: setting both `bearerSecretRef` and an `Authorization` header, which is two authors disagreeing and where guessing sends the audit trail with the wrong credential — case-insensitively, since header names are and config files are written by hand — and naming the field on a sink that makes no requests, where it would be silently ignored. A variable that is empty at startup fails the sink loudly instead of delivering unauthenticated, because a receiver would refuse the batch, fold would retry it, and the trail would look delivered while accumulating in the dead-letter file.

## v1.12.1 — 2026-08-13

Per-caller upstream credentials were only half-implemented; this is the other half.

- **An upstream whose credential comes from the caller now holds one session per principal.** Credentials were already attached per outgoing request, which reads as sufficient and is not: the MCP session itself is established by whichever caller happens to open it, and that identity is durable. The SDK detaches the connection context but deliberately preserves its values, so the `initialize`, the standalone SSE stream, and every reconnect of that stream carried the opening caller's credential for as long as the connection lived. A shared session therefore presented one caller's identity to the upstream while carrying another's bearer on the request — which an upstream that scopes anything to the session it minted is entitled to resolve either way: serve the wrong caller's view, or reject the mismatch, which fold recorded as a transport failure until the breaker opened for everyone. It also meant fold kept re-minting a departed caller's exchanged token from the credential captured in that context. `passthrough` and `token-exchange` upstreams now key their session on `(issuer, subject)` — the same key their token cache already used — and age those sessions out on the sweep that already bounds bridged sessions. Upstreams whose credential is the gateway's own keep the single shared session, and the proxy path is unchanged for them. The regression test asserts at the upstream, because that is the only vantage point from which the crossing was ever visible.
- **`/health` stopped tearing down the upstreams it cannot probe.** A probe runs on nobody's behalf, so a caller-derived credential cannot be resolved for one — and fold pinged anyway, on every poll. Each failure consumed the upstream's rate budget, recorded a circuit-breaker failure (five polls opened the circuit for the callers it was serving perfectly well), and charged the upstream and server budgets once a real session existed. With every upstream in that state `healthy` was zero, so `/health` answered `503` forever and a gateway that worked was never marked ready. Such an upstream is now reported `"unprobed": true` and counts as neither healthy nor unhealthy, with the `503` judged against what the gateway can actually reach; the field is omitted when false, so a federation without caller-derived credentials keeps the exact response it had. `healthCheck` is ignored for those upstreams too, with a warning rather than a validation error — its probe loop ran on a background context and ejected every endpoint on its first round.
- **The exchanged-token fetch gates are bounded.** Each cache key got a fetch mutex, but pruning only dropped the ones whose key was also in the token cache — and an exchange that *fails* never reaches the token cache. Under `token-exchange` the key is `(issuer, subject)`, an identifier the gateway does not choose, and a caller with no grant on that upstream fails on every request, so the map grew with the caller population and never shrank. The gates now carry a waiter count and are dropped when the last caller leaves, bounding them by the fetches in flight rather than the callers ever seen.

## v1.12.0 — 2026-08-13

Governance in both directions, and one seam for judgement fold does not make itself.

- **Deny-by-default now applies to the reverse direction.** Bridged sessions let an upstream reach the caller's client — sampling borrows the caller's model, elicitation asks the caller's human a question — and nothing governed either: a server could spend a caller's model budget in a loop, or put an arbitrary prompt in front of a human, and fold forwarded both without an opinion or a record. `policy.serverInitiatedDecision: "deny"` puts them behind the same engine, matched on server and method, decided against the principal whose in-flight call the request arrived under. Enforcement is the invisibility pair pointed the other way: an upstream that may not ask is never told the caller can answer. It defaults to `allow` for compatibility rather than conviction — that traffic flowed before the check existed — so production deployments set it explicitly.
- **Policy learned depth: deny rules, argument constraints, and annotation gating.** `deny[]` refuses regardless of rule order, because a rule whose correctness depends on where it was pasted will eventually be pasted in the wrong place. `args` constrains a grant by the invocation's own arguments — "may deploy, but only to staging" — with the honest consequence written down: there are no arguments at list time, so a constrained tool is visible and only conditionally callable. And `toolKind` gates on the MCP annotations fold had been ignoring, so one rule can say "read anything, write nothing" — a hygiene control for federations you operate, not a security boundary, since the annotations are declared by the server being gated. Documents using none of it evaluate on exactly the path they did before, measured rather than asserted.
- **fold notices when an upstream rewrites what it advertises.** A tool's description and input schema are the instruction set a model acts on, and fold re-read them on every cache refill and compared them to nothing — so the approval that mattered, a human reading a tool list and accepting the federation, was pinned to nothing. `upstream.pinDefinitions: "warn"` records the digest of every tool and prompt definition and reports a change through the audit trail, a metric, and an alert. It is arithmetic, not judgement: fold never asks whether a description is malicious, only whether it is the same one it served before.
- **The external decision hook, promised since v1.0, exists.** One out-of-process seam — a wire contract rather than a code-loading mechanism — which is what makes declining a plugin runtime honest. It inspects three stages: the invocation (`ingress`), the result (`egress`), and what an upstream asks of the caller's client (`serverInitiated`), the last being where "refuse an elicitation that asks the human for an API key" finally lives. **It decides and cannot rewrite**, which is what keeps the invisibility rule intact. `timeoutMs` and `onError` are required with no defaults, because fold will not guess whether your deployment prefers to stop serving or to keep serving uninspected — and when it fails open, the calls that went uninspected say so in the audit trail. Egress denies *disclosure* rather than effect: by then the upstream has already acted, and the error message says so.

## v1.11.0 — 2026-08-12

The hardening release: two independent production audits, cross-checked, every finding closed.

- **A panic no longer ends the process.** The SDK dispatches each request on its own goroutine with nothing above it to recover, and fold's own fan-out workers, background loops, and notification handlers were equally bare — one nil-dereference triggered by a malformed upstream response took down every session of every tenant, and a trigger in an upstream's steady-state output crash-looped the gateway. Every such site now recovers: the request path answers a generic `-32603` and still exits through audit, loops drop the poisoned tick and continue, and the audit delivery worker reports through the same accounting instead of masquerading as a sink failure. Recoveries count in `fold_panics_total{site}` with a packaged alert, because surviving a panic does not make it not a bug.
- **Abandoned sessions expire.** Ending a session with `DELETE` is optional in the protocol and clients routinely reconnect without it; each abandoned session held gateway state — and the upstream subscriptions it pinned — forever, and the subscription sweeper read the zombies as live. `server.sessionIdleTimeoutMs` (default 30 minutes) is the backstop, and `fold_downstream_sessions` / `fold_upstream_bridged_sessions` make the population watchable.
- **What you deploy is provable.** The three release images and the Helm chart now carry BuildKit provenance, an SBOM, and a sigstore attestation per digest — the binaries had all three since v1.9; the images, the artifact deployments actually run, had none. `checksums.txt` additionally gets a keyless cosign signature for operators outside the `gh` toolchain, every workflow action is pinned to a commit SHA, and base images are pinned by digest — a moved tag on any of them was code execution inside jobs holding release-signing permissions. Verification commands live in [docs/deploy.md](docs/deploy.md).
- **The token endpoint joins the audit trail.** `/oauth/token` is an authorization server, and it produced no audit events: a detected ID-JAG replay — the security event that endpoint exists to catch — was invisible to the SIEM, along with every invalid assertion an attacker fuzzed under the rate limit. Every terminal response now emits one event under `method: "oauth/token"`, with the exchange outcome verbatim in the `decision` field so a replay is alertable on a structured field rather than a substring.
- **JWKS fetches are bounded and straight-line.** The verifier and the EMA exchange ran on `http.DefaultClient` — no timeout, redirects followed — so a wedged IdP could pin verification goroutines forever and whoever answered the JWKS URI could redirect the fetch elsewhere. They now use a dedicated client with the same posture as every other trust-path fetch: 10 s bound, redirects refused. Found by a second, independent audit; the first had recorded these fetches as bounded, which is why cross-checks earn their keep.
- **A Redis outage degrades every primitive to per-instance enforcement — now including rate limits and breakers.** Both failed open to no enforcement at all while budgets, replay protection, and task ownership fell back to local mirrors, and the security model claimed the mirror behavior for everything. Limiters and breakers now keep mirrors fed on every healthy decision, so an outage starts warm; degraded decisions count in `fold_state_degraded_total` with a `FoldStateDegraded` alert. The docs now say exactly what happens.
- **Fold-minted errors stopped narrating internals.** A `-32041` carried the raw transport error — internal endpoint URLs, and on a credential failure the *name* of a secret env var — the same strings `/health` already redacts for untrusted callers. Clients now get `upstream "x" unavailable (details in gateway logs)`; the details are where the message says. And an oversized *chunked* body, which trips the cap mid-read rather than at the Content-Length check, now exits through the same `body_too_large` metric and audit event as everything else.
- **`timeouts.streamIdleMs` exists now — opt-in, not the documented default.** The knob was schema-validated and documented as "120 s" since v1.0 and implemented nowhere. It now cuts a standalone SSE stream that has gone silent so a wedged upstream is retried; it ships opt-in because the SDK client's reconnect budget only replenishes when events arrive, and the documented default would have cycled and eventually killed sessions to upstreams that legitimately never notify. [docs/defaults.md](docs/defaults.md) records the correction.
- **Spans carry no personal data by default.** `enduser.id` was stamped on every server span; trace backends commonly have broader access than the audit trail, which carries the same identity under audit-grade access. `tracing.recordPrincipal: true` opts back in — a deliberate default change, on record in defaults.md.
- **The distroless image can health-check itself.** `fold --healthcheck` probes the local `/health` and exits by result — no shell, no curl needed — and counts *any* HTTP response as healthy on purpose: it answers "is the process serving", and a 503 from every upstream being down must never read as "restart the container".
- **The chart deploys like the checklist says.** An opt-in NetworkPolicy template (the metrics listener's documented security model *is* network scope; optional egress lockdown bounds where a pod holding every upstream credential may connect), PodDisruptionBudget on by default when it protects more than one replica, soft zone/host spread, no service-account token mounted, and NOTES that warn about the two deployments that look fine and are not: multiple replicas without Redis, and discovery without credential allowlists (the gateway now also warns at startup). compose binds loopback — the anonymous-admin Grafana included — and [docs/deploy.md](docs/deploy.md) gains the credential-rotation runbook, whose headline is that hot reload does **not** re-read env vars.
- Smaller bounds, all from the audits: one connect attempt walks at most 3 endpoint candidates instead of every replica; negative timeout/breaker values are rejected (the schema always said minimum 0); poll intervals are floored at 1 s; the in-process jti replay store is size-bounded like every other identifier-keyed store; the public listener gets an `IdleTimeout`; shutdown severs streams that outlive the drain.

## v1.9.0 — 2026-08-11

The console's source leaves the repo; its API gets a name of its own.

**Breaking.** This release renames config fields and endpoint paths with no aliases — the only release that does, and the reason is on record under [API stability](README.md#api-stability). Migration:

| Was (≤ v1.8) | Now (v1.9) |
| --- | --- |
| `GET /console/api/state` | `GET /api/federation` |
| `GET /console/api/auth` | `GET /api/auth-hint` |
| `GET /healthz` | `GET /health` (the alias is removed; a probe left on the old path now 404s) |

| `fold_http_rejections_total{reason="console_viewer"}` | `…{reason="introspection_viewer"}` — a dashboard or alert selecting the old value stops matching **silently**, with no error anywhere |
| audit denial `error: "principal not in console viewer allowlist"` | `"principal not in introspection viewer allowlist"` — update any SIEM rule matching that string |

- **The console's assets move to [fold-run/fold-console](https://github.com/fold-run/fold-console).** A hand-written browser app was living in a Go repo whose review discipline is built for a proxy path, released on that proxy's cadence. The source now has its own repo, its own contributors, and its own cadence; `gateway/console/` is vendored output pinned to a commit, verified by CI, and still embedded — so what a fold binary serves is exactly what it served before. The assets stay checked in rather than fetched at build time because the Go module proxy is fold's distribution channel: `go run github.com/fold-run/fold/cmd/fold@latest` must build from the proxy zip alone, which runs no generators and carries no submodules.
- **`server.introspection`** — the read APIs are no longer the console's private detail. `/api/federation` reports configuration truth that `/metrics` structurally cannot: the effective policy default and rule count, audit sink types, whether shared state and tracing are on, discovery's last sync, and the viewer's tenant governance. It is separately configurable because an operator scripting against the federation snapshot should not have to serve a browser page to get it. `introspection.groups` is the viewer allowlist, unchanged in meaning and moved to where it belongs — it gates the API, and the API now has more than one consumer. The response shape joins the frozen wire surface.

## v1.8.0 — 2026-08-10

Tenancy: the customer becomes an object instead of an assembly.

- **`tenants[]`** — a named set of principals plus the governance that applies to them as a group, matched from the same verified claims policy already matches on. Before this, "team A sees these tools, gets this allowance, and appears separately in audit" was assembled from four unrelated mechanisms and the word *tenant* appeared nowhere in the config, the audit stream, or the metrics. The line the design holds above all: **a tenant groups principals; it does not authenticate them** — it is derived from the verified `auth.Principal`, never presented alongside a token, and policy remains the authority on what may be invoked. Reloadable, unlike `server.budget`: tenants change when a customer signs up. Additive by construction — declare none and nothing changes.
- **One allowance and one bucket per team.** `tenants[].budget` is the dimension consumption governance actually wanted: `perPrincipalPerMinute` gives each *person* a bucket, so ten agents on one team hold ten allowances, while a tenant shares one — which is what "team A cannot flood team B" means. Budgets charge narrowest-first (upstream → tenant → server) so a refusal never spends a wider allowance, and buckets check widest-first (global → tenant → per-principal) so a flood is refused before it costs any routing work.
- **`tenants[].upstreams` bounds what a tenant can see**, evaluated *before* policy. It filters the **fan-out**, not the result: an upstream outside the subset is never asked, so it costs no request, no budget, and no partial-failure entry when it is down. Named invocations against it are refused ahead of the policy engine with `-32042` — except `tasks/*`, which answer "no upstream owns that id", the posture that path already takes for another principal's task, because there a refusal must not reveal existence.
- **A principal resolves to at most one tenant, and ambiguity is refused rather than guessed.** Assigning by precedence would hand a caller another customer's allowance and visibility the day someone reorders a list. Selector overlap cannot be decided statically — it is only decidable against a real principal — so validation catches what is genuinely checkable and the rest is caught at request time.
- **Resolution is flat in the number of tenants.** The two selector shapes a per-customer document repeats — one claim equalling one value, or one group — are indexed at snapshot time, keyed from opposite sides: the claim index by what the tenant requires, the group index by what the principal holds. Ten thousand tenants resolve in **97 ns, zero allocations**, the same as ten; a scan cost 450 µs at that size ([benchmarks](docs/benchmarks.md#tenant-resolution-cardinality)). Compound selectors still scan, so keep those in the tens.
- **In the record** — `tenant` on every audit event its principals produce, denials included, plus `fold_tenant_requests_total{tenant,outcome}` and `fold_tenant_upstream_calls_total{tenant}`, the second counting the unit a budget is charged in. These are new metric *names* rather than a `tenant` label on the existing ones: label sets are frozen by the compatibility contract, and a new label would break every dashboard built on them. The console's federation view is now the *viewer's* — a tenant with a subset sees its own upstreams and its own limits, closing the one place a dashboard could show a customer the topology its own traffic is refused.
- **Helm: `appVersion` is the image users actually get.** `values.yaml` ships `image.tag: ""` and the deployment falls back to `Chart.AppVersion`, which had not moved since v0.4.0 — so a default `helm install` deployed a pre-1.0 gateway. Fixed, and the release flow now bumps it, verified by re-rendering the chart rather than by inspecting the edit.
- **The console adopts the current fold.run design system.** Its tokens still carried the previous identity: a mint accent on every button, three radii, and the mark-plus-text lockup the drawn wordmark replaced. Live (`#D6FF00`) is now licensed to proof alone — status-up and the focus ring — while actions run the neutral ramp on a Signal-white fill, and every corner is machined at 2px. Two deliberate departures from the marketing spec, both recorded at the token: controls are 34px rather than 44px, because a console stacks a token field, a picker, and three mode buttons above a table; and a half-open breaker reads on the neutral ramp rather than in amber, because the palette has no third hue and a half-open breaker is not proof of anything. Landed in `a474025`, whose message describes only the Helm fix above.

## v1.7.0 — 2026-08-08

Consumption governance: what was spent, by whom, and a ceiling on it.

- **Budgets** — `server.budget` and `upstreams[].budget` cap consumption over a calendar period (`hour`/`day`/`month`, UTC-aligned) that **accumulates** until it rolls over. This is the question `rateLimit` cannot answer: a sliding window smooths a burst and forgets it, a budget remembers. Absent by default — a default allowance is a default outage waiting for a busy month. `server.budget` is construction-wired like the rest of that section, so an allowance cannot be widened under a running gateway by editing config.
- **The unit is upstream invocations, not client requests.** One `tools/list` fans out to every upstream, so counting client requests would price a list the same as a ping. The new `upstreamCalls` audit field and `fold_request_upstream_calls` histogram make that fan-out visible in its own right.
- **Exhaustion mints `-32044`** and the `budget_exhausted` audit outcome, distinct from `-32040` because the remedies differ: a rate limit clears in seconds, a budget not until the period rolls. The message names the reset instant rather than a retry delay — a client backing off by a monthly reset would sleep for a fortnight.
- **Budgets are checked where the invocation really happens**, after the session is in hand, so a rate limit, an open circuit, or a failed connect never spends the allowance. Without that, an upstream down for a month would burn tens of thousands of units on calls nobody served.
- **Metering** — additive audit fields recording what fold observed and nothing it did not: `upstreamCalls`, `itemsServed` (what a list handed *this* caller, after policy filtering), and `usage` carried verbatim from an upstream's result `_meta`. There is no tokenizer in the gateway; fold governs MCP consumption, not model spend, and an installation needing both runs both. The reasoning is on record in [docs/design-consumption.md](docs/design-consumption.md).
- **Fail-open, but loud** — a budget check that cannot reach shared state degrades to per-instance enforcement rather than to none, and says so via `fold_budget_degraded_total`. Alert on any non-zero rate: it means the fleet is not enforcing one allowance. The gateway also warns at startup when a budget is configured without shared state.

## v1.6.0 — 2026-08-08

Local MCP servers join the federation, and the list path stops rebuilding what it already holds.

- **`fold-stdio`, the shim for local servers** — fold federates HTTP endpoints, but most MCP servers are stdio processes. The shim runs one of them and serves it over streamable HTTP, so it joins the federation as an ordinary `url` upstream: credential strategies, health checks, load balancing, breakers, timeouts, policy, pagination, and audit all apply with no special case, and nothing in the config document changed. Ships as its own binary, image (`ghcr.io/fold-run/fold-stdio`), and compose profile — see [docs/stdio.md](docs/stdio.md), and [docs/design-stdio.md](docs/design-stdio.md) for why process supervision lives in a sidecar rather than in the gateway.
- **The command never comes from the network** — it is fixed at the shim's argv, never taken from a request, a config document, or discovery. A `command` field in the config would hand whoever controls the discovery document an `exec` on the gateway host, reducing `allowedSecretRefs` and `allowedCredentialHosts` to formalities. The child's environment is an explicit allowlist rather than an inheritance, one process serves one session (a stdio connection carries exactly one MCP session, so sharing one would share a JSON-RPC id space), children run in their own process group so a wrapper's grandchildren cannot survive teardown, and a non-loopback bind without `--bearer-env` is refused at startup.
- **Warm list hits stop re-decoding** — `cachedList` ran `json.Unmarshal` over the full serialized list on every warm hit, per upstream, and the egress namespace rewrite copied every tool and rebuilt every name per request. Both are now memoized against the identity of the cached bytes, which makes the memo self-invalidating and keeps it off for upstreams whose caching is disabled because their credential is caller-derived. A warm hit is **~55 ns and one allocation regardless of list size**.
- **Policy filtering allocates nothing** — `globMatch` re-split its pattern on `*` for every evaluation, one allocation per item on every `tools/list`. Patterns come from config and never change for the life of an engine, so they compile when the engine is built. Filtering 1,000 tools per principal is now CPU only.
- **Federation cost is measured** — the added-latency gate uses one upstream with one trivial tool, so nothing in CI observed the work that scales with federation size. `BenchmarkFederatedListTools` covers the merge path directly: a 20 × 50 federation merges 1,000 tools in **25 µs**. Methodology and the full table in [docs/benchmarks.md](docs/benchmarks.md).
- **A roadmap** — [docs/roadmap.md](docs/roadmap.md) records what fold intends to build and, more usefully, what it declines to build and why.
- Dockerfiles move to [`deploy/docker/`](deploy/docker); `azure/setup-helm` bumped off deprecated Node 20.

## v1.5.0 — 2026-08-07

Hardening, and task ownership the whole fleet agrees on.

- **Fleet-wide task ownership** — the `taskId → (upstream, minting principal)` index moves out of process memory into a shared-state primitive, so with `REDIS_URL` (or `server.redisUrl`) set every instance reads the same ownership: a caller can no longer reach another principal's task by landing on an instance that did not serve the mint, and the binding survives a rolling restart. Redis is authoritative on reads, every write is mirrored locally, and an outage falls back to that mirror rather than to no records. Entries key on a digest of the task id and hold a digest of the owning principal; `tasks/list` resolves a whole page in one batch read. Records expire after 24 hours and a gateway without Redis is still per-instance — both fall through to the existing locate-by-probe path.
- **`/health` replaces `/healthz`** — the health path is now `/health`. `/healthz` answers identically as a deprecated alias (`Deprecation: true`, plus one log line on its first use so you can find what still probes it) and is removed no sooner than the next major; point probes at `/health`. Applies to `fold-discovery` too, where the old path would otherwise have fallen through to its document handler.
- **`/health` is no longer a load amplifier** — every call used to fan a live MCP ping to every upstream, unauthenticated and outside the rate limiter. The fan-out is now single-flighted and reused for a second, invalidated immediately by a reload or discovery sync, so polling it in a loop costs at most one collection per second.
- **Subscriptions are released when their client goes away** — `resources/unsubscribe` was the only path that decremented the ref count, so a client that subscribed and disconnected left the gateway holding an upstream subscription indefinitely. The idle sweeper now reaps them and drops the shared upstream subscription with the last live subscriber.
- **Credential paths hardened** — the token endpoint's response body is bounded and its fetches are single-flighted per identity (a burst of first-time callers for one principal became a burst of grant requests, each carrying the client secret and that caller's own bearer token); the discovery poller and the audit webhook now refuse redirects, as the token-endpoint client has since v1.0.1.
- **Stricter host matching, bounded stores** — a non-numeric port in `Host` or `Origin` is rejected rather than split at the last colon, closing a rebinding bypass where `localhost:8080.evil.com` read as the allowed host `localhost`; and the per-instance affinity caches (resource-URI ownership, the per-principal limiter memo) are size-bounded.

## v1.0.1 — 2026-08-04

**Security fix**, released from the `release-1.0` branch as a drop-in patch. The token-endpoint client followed HTTP redirects, and Go replays POST bodies on 307/308 — so a redirecting token endpoint handed the grant to the redirect target: the client secret under `client_secret_post`, and the caller's own bearer token as `subject_token` under `token-exchange`. Affects any upstream using `client-credentials` or `token-exchange` whose token endpoint can be made to redirect. The client now refuses every redirect and the grant fails closed.
